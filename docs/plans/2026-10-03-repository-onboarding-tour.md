# Development Plan — Repository Onboarding Tour (five-section generated tour, repo-scoped studio page)

## Source requirements
`specs/2026-10-03-repository-onboarding-tour.md` (SPEC-2026-10-03-repository-onboarding-tour) — covers **AC-1 … AC-23** (all). All four former NEEDS-CLARIFICATION items are pinned in the spec's "Resolved decisions" (2026-10-03): external hosting-provider link for Open (AC-19); session-local read-progress/step-completion (AC-15/16); first tasks from open PRs only; presentation specifics verified against the mockups.

## Goal
An explicit user action turns the intelligence DevDigest already has (repo-intel index, clone artifacts, open PRs) into one persisted, mechanically-grounded five-section onboarding tour per repo, rendered as a repo-scoped studio page with TOC/scroll-spy, copy/run-step tracking, Regenerate and Share — zero model calls to read, ≤1 model call (budget 5) to generate, previous tour never lost to a failed run.

## Binding constraints
- Onion placement per touched ring (`onion-architecture` is THE authority for `server/`): routes transport-only (zod `params`/`response` via `fastify-type-provider-zod`, no hand-rolled `Schema.parse`); repository is the only file touching `t.onboarding`; cross-module data (pulls, repo-intel, settings) only via the container; no new port/adapter — everything consumed already exists.
- Vendor sync: Task 1's contract file mirrored **byte-identically** into both `src/vendor/shared` copies; typecheck BOTH server and client (CI diffs the whole tree).
- **No migration** — the `onboarding` table is used as-is; `migrations/` untouched (append-only rule respected by not generating anything).
- No new dependencies in any package; lockfiles untouched. Client rendering uses the vendored `Markdown` + existing `MermaidDiagram` + `mermaid` dep only.
- Naming per AGENTS.md: PascalCase component files + colocated `_components/<Name>/` with `index.ts` barrels; kebab-case modules; DB-backed server tests end `*.it.test.ts`; e2e flow `specs/NN-name.flow.json`; user-visible client copy only via next-intl (`messages/en/onboarding.json`).
- Untrusted-content rules: clone/doc/PR text enters the prompt only inside `wrapUntrusted(...)`; the model's output is contract-validated and mechanically grounded before persist; tour prose/diagram render as data (AC-21); run-step commands are display/copy text, never executed; INJECTION_GUARD text untouched.
- Regeneration replaces the single row **whole** in one upsert, only after the finished document passes `OnboardingTour.parse` (AC-2/AC-4).
- Spec-update rule: root spec exists → Task 12 flips its Status line; no `server/specs/` file is created (would duplicate the root spec).
